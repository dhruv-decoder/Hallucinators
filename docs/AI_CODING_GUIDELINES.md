# AI-Assisted Coding Guidelines — Team Hallucinators

We use AI to write a lot of this code. That is fine and expected. What is **not** negotiable: the repo must
read like a careful engineering team wrote it, every author can explain every line with their name on it, and
every claim we publish is true and traceable. These rules apply to humans and to any AI coding assistant we
run. Paste this file into the assistant's context at the start of every session.

## 1. Voice & comments — write like an engineer, not a chatbot
- **No AI-tell comments.** Never write "As an AI…", "Here we elegantly…", "This cutting-edge/revolutionary…",
  "Note: I have…", "Certainly!", or narration of the assistant's own process.
- **No marketing words in code or docstrings:** *seamless, blazing-fast, robust, powerful, state-of-the-art,
  world-class, revolutionary, elegant.* Describe what the code does and why, plainly.
- **No emojis in source code**, commit messages, or identifiers.
- Comments explain **why**, not **what** the line obviously does. Delete comments that just restate the code.
- Match the surrounding file's style, naming, and comment density. Consistency over personal preference.

## 2. Documentation — thorough, honest, and current
- Every public module/class/function has a **docstring**: purpose, params, returns, raises, and any assumption
  or reference (e.g. "groundedness via HHEM-2.1; see EVIDENCE.md#hhem").
- Keep `ARCHITECTURE.md` current as the system changes. Record every non-obvious choice as a short ADR in
  `DECISIONS.md` (context → decision → consequences).
- The `README.md` must let a stranger run the prototype from a clean clone with **one command**. If a step is
  undocumented, it is broken.
- Comments and docs must match the code. If you change behavior, update the docs in the same PR.

## 3. No fabricated facts — ever (this is how we lose or win the jury)
- **No invented numbers, benchmarks, citations, dates, or incidents** anywhere — code, comments, docstrings,
  README, slides, or video.
- Every external statistic or claim links to a **primary source** in `EVIDENCE.md`. Every internal
  performance number is regenerated by `make eval` — if a command doesn't produce it, it doesn't get published.
- If you don't know a value, write a clearly-labeled `TODO(owner): measure X` — never a plausible-looking
  placeholder that could be mistaken for a real result.
- Cite the real papers/models for techniques we use (Semantic-Entropy Probes, MiniCheck, HHEM, GLiNER,
  RouteLLM, Llama Guard / ShieldGemma / PromptGuard-2). Get authors and behavior right; don't overclaim.

## 4. Stay in the loop — you must be able to defend it
- The owner of a module **reads every line** the AI produced and can explain it live in the AI discussion.
- If you can't explain a block, **rewrite it** until you can, or delete it. Cleverness you don't understand is
  a liability, not an asset.
- Prefer the boring, readable solution over the impressive one-liner.
- Never paste large AI output unread. Never merge code no human has run.

## 5. Correctness & reproducibility
- **Pin dependencies** (`pyproject.toml` with exact versions). No "latest".
- **Seed everything** random. The eval must be deterministic run-to-run.
- Unit-test anything with real logic — especially the VoI math (`voi.py`), the stopping rule, calibration, and
  the P&L ledger. These are the claims; they get tests.
- Type-hint public interfaces. Run a linter/formatter (ruff + black) and a type check (mypy where practical)
  before every PR. Keep `main` runnable at all times.
- No secrets in the repo. `.env` is gitignored; `.env.example` documents every key.

## 6. Hygiene
- Small PRs (< ~400 lines) with a description of what changed and why. P1 reviews and merges.
- No dead code, no commented-out blocks "just in case", no unused deps. Delete freely; git remembers.
- Respect dataset and model **licenses**; record each in `EVIDENCE.md`. Attribute OSS models we ship.
- Commit messages: imperative, plain, explain the why. No emojis, no AI narration.

## 7. Definition of Done (per task)
1. Runs from a clean clone. 2. Has docstrings + a test where logic is non-trivial. 3. Docs updated in the same
PR. 4. No fabricated values; new numbers come from `make eval` or a sourced entry in `EVIDENCE.md`. 5. The
owner can explain every line.

> If an AI assistant proposes anything that violates §3 (fabrication) or §4 (unexplainable code), stop and fix
> it before continuing. Those two rules are what protect us in front of the jury.
